# Phase 1 Data Model: Provider Keys

## Supporting Types and Private Ownership Helper

The migration first ensures `supabase_vault` is available (`CREATE EXTENSION IF NOT EXISTS supabase_vault CASCADE`) and introduces types shared by provider-key records and future generation records:

```sql
CREATE TYPE provider_t AS ENUM ('openai', 'gemini');
CREATE TYPE provider_key_lifecycle_t AS ENUM ('normal', 'cleanup_required');
CREATE TYPE brand_deletion_state_t AS ENUM ('active', 'cleanup_required');
```

It also introduces the deferred ownership helper anticipated by the Brand CRUD research
in a schema that is not listed in Supabase's exposed API schemas:

```sql
CREATE SCHEMA IF NOT EXISTS private;
REVOKE ALL ON SCHEMA private FROM PUBLIC, anon, authenticated;
GRANT USAGE ON SCHEMA private TO authenticated, service_role;

CREATE FUNCTION private.is_brand_owner(p_brand_id UUID)
RETURNS BOOLEAN
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path = ''
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM public.brands
    WHERE id = p_brand_id
      AND owner_user_id = (SELECT auth.uid())
  );
$$;

REVOKE ALL ON FUNCTION private.is_brand_owner(UUID) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION private.is_brand_owner(UUID) TO authenticated, service_role;
```

The `private` schema is deliberately absent from `supabase/config.toml`'s exposed API
schemas, so PostgREST cannot publish the helper as an authenticated RPC. `authenticated`
and `service_role` receive schema `USAGE` plus exact function `EXECUTE` because RLS
policies run under the querying role; they receive no schema `CREATE`. Execution remains
revoked from `PUBLIC`. The empty search path and fully qualified names prevent
object-shadowing attacks in a `SECURITY DEFINER` function.

## Existing Entity Change: Brand

The existing `brands` table gains one field:

| Field | Type | Rules |
|---|---|---|
| `deletion_state` | `brand_deletion_state_t` | `NOT NULL DEFAULT 'active'` |

`cleanup_required` means a user-requested hard delete did not complete. The physical row remains visible solely as the retry anchor; provider-key and brand-asset mutation is blocked. This is not soft deletion: there is no completed-deletion state or `deleted_at`, and successful deletion physically removes the row.

The migration broadens `logo_path` to token-owned paths: `brands/{brand_id}/logos/{operation_token}.{ext}` while retaining compatibility with existing legacy `brands/{brand_id}/logo.{ext}` rows. New uploads always use tokenized paths. Because each operation owns a unique object key, stale compensation can delete only its own object and can never delete a newer upload.

The existing foreign key from `brands.owner_user_id` to `auth.users` changes from `ON DELETE CASCADE` to `ON DELETE RESTRICT`. Otherwise deleting an auth user directly could bypass the hard-delete coordinator and orphan Vault/Storage assets. Account deletion must clean owned brands first.

Authenticated clients no longer receive direct `INSERT`, `UPDATE`, or `DELETE` privileges on `brands`; all mutations remain backend-mediated. Existing owner `SELECT` remains available under RLS.

A `BEFORE UPDATE` trigger rejects `deletion_state = 'cleanup_required'` transitioning back to `active`. Only successful physical deletion completes cleanup.

## Entity: Provider Key

Maps to the new `provider_keys` table. A row contains only safe metadata and an opaque Vault UUID; raw credentials never enter this table.

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key, generated by the application before Vault creation |
| `brand_id` | UUID | Required FK to `brands(id) ON DELETE RESTRICT`; owner tenancy boundary |
| `provider` | `provider_t` | Required; `openai` or `gemini` |
| `vault_secret_id` | UUID | Required, unique opaque reference; never client-visible; no FK into extension-owned Vault internals |
| `label` | TEXT, nullable | At most 100 characters |
| `key_hint` | TEXT | Required safe value matching `***` plus four `[A-Za-z0-9_-]` characters; already client-formatted |
| `lifecycle` | `provider_key_lifecycle_t` | Required, default `normal` |
| `is_active` | BOOLEAN | Required, default `false` |
| `is_valid` | BOOLEAN, nullable | `NULL` = unvalidated, `true` = valid, `false` = invalid |
| `last_validated_at` | TIMESTAMPTZ, nullable | Set only for completed valid/invalid outcomes |
| `last_validation_error` | TEXT, nullable | Safe code; currently only `INVALID_CREDENTIAL`, never provider text or key material |
| `validation_token` | UUID, nullable | Fencing token while one validation is in progress; not client-visible |
| `validation_lease_expires_at` | TIMESTAMPTZ, nullable | Database-clock expiry paired with token; not client-visible |
| `last_used_at` | TIMESTAMPTZ, nullable | Reserved for the later generation phase; not exposed in this phase |
| `created_at` | TIMESTAMPTZ | Required, default current time |
| `updated_at` | TIMESTAMPTZ | Required, maintained by existing `set_updated_at()` trigger |

### Database Constraints

```sql
CHECK (label IS NULL OR char_length(label) <= 100)
CHECK (key_hint IS NOT NULL AND key_hint ~ '^\*\*\*[A-Za-z0-9_-]{4}$')
CHECK (lifecycle <> 'cleanup_required' OR NOT is_active)
CHECK (is_valid IS DISTINCT FROM false OR NOT is_active)
CHECK (last_validation_error IS NULL OR last_validation_error = 'INVALID_CREDENTIAL')
CHECK (
  (validation_token IS NULL AND validation_lease_expires_at IS NULL)
  OR
  (validation_token IS NOT NULL AND validation_lease_expires_at IS NOT NULL)
)
CHECK (lifecycle = 'normal' OR validation_token IS NULL)
CHECK (
  (is_valid IS NULL AND last_validated_at IS NULL AND last_validation_error IS NULL)
  OR (is_valid IS TRUE AND last_validated_at IS NOT NULL AND last_validation_error IS NULL)
  OR (is_valid IS FALSE AND last_validated_at IS NOT NULL AND last_validation_error = 'INVALID_CREDENTIAL')
)
```

The raw key request model applies the matching boundary validation before Vault access: at least five characters, non-whitespace, and a final-four suffix matching `[A-Za-z0-9_-]{4}`. It also rejects a label containing the submitted raw key.

A `BEFORE UPDATE` trigger rejects `lifecycle = 'cleanup_required'` transitioning back to `normal`. Cleanup-required is irreversible; successful cleanup physically removes the row.

### Indexes

```sql
CREATE UNIQUE INDEX uq_provider_keys_vault_secret
  ON provider_keys(vault_secret_id);

CREATE UNIQUE INDEX uq_provider_keys_one_active
  ON provider_keys(brand_id, provider)
  WHERE is_active;

CREATE INDEX idx_provider_keys_brand_provider_created
  ON provider_keys(brand_id, provider, created_at DESC, id DESC);

CREATE INDEX idx_provider_keys_cleanup
  ON provider_keys(brand_id, lifecycle)
  WHERE lifecycle = 'cleanup_required';
```

The partial unique index is the final concurrency invariant for one active key per provider. Application row locking controls the expected transition, while the index protects against bugs and unexpected writers.

### Relationships

- One brand owns zero or more provider-key rows.
- Every provider-key row belongs to exactly one brand.
- A row references exactly one Vault secret UUID. The identifier is deliberately not a foreign key to extension-owned `vault.secrets`; deletion retry treats an already-absent secret as clean.
- A logical Secret Cleanup Reference is represented by a provider-key row with `lifecycle = 'cleanup_required'`, not a separate table.
- The restrictive FK prevents the brand row from disappearing while any normal or cleanup-required key reference remains. The deletion service explicitly removes Vault secrets and provider-key rows before hard-deleting the brand.

## Entity: Provider-Key Idempotency Receipt

Maps to `provider_key_idempotency`. It contains no credential or hint and prevents delayed add retries from recreating a key after deletion.

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Internal primary key |
| `brand_id` | UUID | Required FK to `brands(id) ON DELETE CASCADE` |
| `request_id` | UUID | Client `Idempotency-Key`; unique with `brand_id` |
| `provider_key_id` | UUID, nullable | FK to `provider_keys(id) ON DELETE SET NULL` |
| `state` | TEXT | `active` or `deleted` |
| `created_at` | TIMESTAMPTZ | Required current time |

The receipt and key/Vault creation commit in one transaction. An `active` receipt returns its existing safe key on retry. Individual key deletion atomically changes the receipt to `deleted` before removing the key; subsequent add retry returns `IDEMPOTENCY_KEY_RETIRED`. Receipts persist until the owning brand is hard-deleted, at which point their safe rows cascade because they have no external asset.

The table uses `ENABLE`/`FORCE RLS` with the same owner predicate but grants no privileges to `anon` or `authenticated`; only the backend role may read/write receipts. Integration tests require direct-role and Data API denial for SELECT/INSERT/UPDATE/DELETE, including same-owner references.

## Entity: Brand Asset Operation

Maps to `brand_asset_operations`. This backend-only durable operation record fences external Storage writes; unlike a lease, it never expires automatically.

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key and operation token |
| `brand_id` | UUID | Required FK to `brands(id) ON DELETE RESTRICT` |
| `operation` | TEXT | `upload` or `remove` |
| `object_path` | TEXT, nullable | Token-owned upload path or captured removal path |
| `previous_path` | TEXT, nullable | Prior logo path that replacement must clean before operation completion |
| `state` | TEXT | `in_progress` or `cleanup_required` |
| `remote_status` | TEXT | `pending`, `succeeded`, `failed`, or `unknown` |
| `started_at` | TIMESTAMPTZ | Required database time |
| `updated_at` | TIMESTAMPTZ | Required database time |

Before external Storage I/O, the backend locks the active brand, verifies no asset operation already exists, and inserts this row. A unique index on `brand_id` enforces at most one asset operation per brand, serializing upload/removal and preventing overlapping replacements from sharing a previous path. Replacement records both its unique target and previous path. Normal upload success updates `logo_path`, removes the previous object, verifies it absent, and only then deletes the operation row. If previous-object cleanup fails, the new logo may remain referenced but the operation becomes cleanup-required and blocks further mutation/deletion until old-object cleanup completes. A definitive pre-write Storage failure can clear the row only when no object was written; an ambiguous timeout/crash sets `remote_status = 'unknown'`, enters cleanup-required, and blocks brand deletion.

Elapsed time, polling, or temporary object absence alone never converts `unknown` to a terminal state. The operation row is removed only after a definitive remote outcome is established and every operation-owned/previous path is confirmed absent as required. If no terminal outcome can be established after a crash, the operation remains cleanup-required and brand deletion remains blocked for operator recovery rather than falsely reporting hard-delete success.

Startup and request-time reconciliation detect abandoned `pending` rows and mark them `unknown`/cleanup-required; they never silently expire them. Brand deletion may transition to cleanup-required only when no `brand_asset_operations` rows exist. Once fenced, new operation rows are rejected, so the Storage prefix can only shrink.

This table uses `ENABLE`/`FORCE RLS`, no `anon`/`authenticated` grants, and backend-only DML. Integration tests require direct-role and Data API denial for every operation, including same-owner brands. Its restrictive FK prevents brand deletion while any in-flight or unresolved external write exists.

## State Transitions

### Provider-key lifecycle

| From | Event | To | Required effects |
|---|---|---|---|
| none | Add key succeeds | `normal` | Vault secret and row commit atomically; optional activation follows one-active invariant |
| `normal` | Delete requested | `cleanup_required` | Set inactive; clear validation lease, validity, validation timestamp/error; commit durable retry anchor |
| `cleanup_required` | Cleanup retry succeeds | row absent | Vault secret and row removed atomically |
| `cleanup_required` | Cleanup retry fails | `cleanup_required` | Remain inactive and owner-visible; normal operations blocked |

There is no transition from `cleanup_required` back to `normal`; replacing or editing raw keys is out of scope.

### Validation state

| Current state | Outcome | New state |
|---|---|---|
| any normal state | Accepted by provider | `is_valid=true`, timestamp set, safe error cleared; active state preserved |
| active/unvalidated or active/valid | Explicit authentication rejection | `is_valid=false`, timestamp/error set, `is_active=false` |
| inactive | Explicit authentication rejection | `is_valid=false`, timestamp/error set, remains inactive |
| any | Temporary/unknown/timeout | Validation and active fields unchanged |
| invalid | Successful revalidation | `is_valid=true`; eligible for later explicit activation, not auto-activated |

Only one unexpired validation lease may exist per key. Completion updates require the matching fencing token. An expired or stale token cannot alter state.

### Brand deletion state

| From | Event | To |
|---|---|---|
| `active` | Confirmed deletion starts | `cleanup_required`; allowed only with no asset-operation rows; all keys become cleanup-required/inactive; new asset/key operations blocked |
| `cleanup_required` | Storage or Vault cleanup fails | remains `cleanup_required`; retry allowed, mutations blocked |
| `cleanup_required` | All cleanup succeeds | brand row, keys, and Vault secrets physically absent |

## Row Level Security, Safe Read View, and Grants

```sql
ALTER TABLE provider_keys ENABLE ROW LEVEL SECURITY;
ALTER TABLE provider_keys FORCE ROW LEVEL SECURITY;

CREATE POLICY provider_keys_select ON provider_keys
  FOR SELECT USING (private.is_brand_owner(brand_id));

CREATE POLICY provider_keys_insert ON provider_keys
  FOR INSERT WITH CHECK (private.is_brand_owner(brand_id));

CREATE POLICY provider_keys_update ON provider_keys
  FOR UPDATE
  USING (private.is_brand_owner(brand_id))
  WITH CHECK (private.is_brand_owner(brand_id));

CREATE POLICY provider_keys_delete ON provider_keys
  FOR DELETE USING (private.is_brand_owner(brand_id));

GRANT SELECT, INSERT, UPDATE, DELETE ON provider_keys TO service_role;

GRANT SELECT (
  id, provider, label, key_hint, lifecycle,
  is_active, is_valid, last_validated_at, last_validation_error, created_at
) ON provider_keys TO authenticated;
```

Authenticated receives no table `INSERT`, `UPDATE`, or `DELETE`, and no `SELECT` on `brand_id`, `vault_secret_id`, creation/validation tokens, lease fields, `last_used_at`, or other internal columns. Direct safe-column table reads are owner-filtered by RLS; no separate view is required. Cleanup transition clears validation fields, so direct safe reads match the cleanup response contract.

The migration replaces the prior table-level authenticated grant on `brands` with safe-column `SELECT` only (`id`, `name`, `logo_path`, `deletion_state`, `created_at`, `updated_at`) and no writes. This prevents direct owner deletion from bypassing Storage/Vault cleanup. The backend continues to apply owner predicates while using a privileged database connection.

Before replacement grants, the migration executes `REVOKE ALL ON provider_keys FROM PUBLIC, anon, authenticated` and revokes the existing table-level authenticated privileges on `brands`. It then grants only the safe column reads listed above and the required backend/service privileges.

The `DATABASE_URL` role must be private and have `rolbypassrls = true` (or be superuser); table ownership is insufficient under `FORCE ROW LEVEL SECURITY`. Startup checks require that property plus DML/Vault privileges. Local development uses `postgres`; hosted deployment uses a private equivalent. The browser-facing `anon`/`authenticated` roles never satisfy this check.

## Vault Security Boundary

- Raw values live only in `vault.secrets` and are read through `vault.decrypted_secrets` by the backend database role.
- `vault` is not an exposed Data API schema.
- `PUBLIC`, `anon`, and `authenticated` receive no `USAGE`, `SELECT`, `DELETE`, or Vault function execution privileges. Revokes use exact installed function identities: `vault.create_secret(text,text,text,uuid)` and `vault.update_secret(uuid,text,text,text,uuid)`.
- A hosted `DATABASE_URL` role receives only the Vault privileges this feature uses: schema `USAGE`; `EXECUTE` on `vault.create_secret(text,text,text,uuid)`; `SELECT (id, decrypted_secret)` on `vault.decrypted_secrets`; and `SELECT (id), DELETE` on `vault.secrets`. It does not receive `update_secret` execution. The documented local `postgres` exception may retain broader extension-owned privileges; Supabase's built-in `service_role` may also retain extension-owner grants and is never accepted as the hosted database login.
- Startup/integration checks fail closed if the configured backend role lacks required Vault/application privileges or `BYPASSRLS`/superuser behavior required by forced RLS.
- Tests verify catalog privileges, direct-role denial with SQLSTATE `42501`, and Data API rejection even for the owner of the corresponding provider-key record.

## Scale Assumptions

MVP users are expected to retain a small number of keys per brand (normally one active and a few historical inactive keys per provider). List responses are unpaginated, ordered by provider then newest-first. The indexes above support deterministic lookup and cleanup without introducing a product limit.
